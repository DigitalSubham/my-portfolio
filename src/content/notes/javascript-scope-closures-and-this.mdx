Ten topics. Between them they produce more interview questions than anything else in JavaScript. Closures alone open perhaps a third of all screening rounds.

The good news: they are all the same idea seen from different angles. A function remembers where it was written. Get that, and the rest follows.

## Lexical scope and the scope chain

**In simple words:** where a variable is available is decided by *where you wrote the code*, not by where you call it from. JavaScript decides this when it reads your file, before anything runs.

When a function needs a variable, it looks in its own body first. Not there? It looks at the function that wrapped it. Still not there? It keeps going outward until it reaches the global scope. That chain of lookups is the **scope chain**.

<Callout variant="careful">
Lexical means "decided by position in the source". This is the whole reason `this` confuses people later: `this` is the one thing that is **not** lexical in a normal function. It is decided at call time, not write time.
</Callout>

## Closures

**In simple words:** a closure is a function that still remembers the variables around it, even after the function that created those variables has finished.

That is the entire definition. The confusion comes from the fact that it sounds like it should be impossible.

```js
function makeCounter() {
  let count = 0;                 // outer finishes, but this survives

  return function () {
    count += 1;
    return count;
  };
}

const next = makeCounter();
next();  // 1
next();  // 2
next();  // 3

const other = makeCounter();
other(); // 1  -- a completely separate count
```

`makeCounter` returned and its call finished. Normally `count` would be discarded. But the returned function still refers to it, so JavaScript keeps it alive.

<Callout variant="analogy">
A function leaving home with a backpack. Inside the backpack are the variables it was using. The house gets demolished, but the function still has the backpack.

Each call to `makeCounter` packs a **new** backpack. That is why `next` and `other` count separately.
</Callout>

<Callout variant="careful">
Closures have a memory cost. A closure keeps its captured variables alive for as long as the closure itself lives. Attach a closure to an event listener, a timer or a global cache and forget to clean it up, and you have a memory leak.
</Callout>

<Callout variant="interview">
"A closure is a function bundled with the scope it was created in. When an inner function references an outer variable, that variable survives after the outer function returns, because the inner function still holds a reference to it. Each call to the outer function creates a fresh set of variables, so closures made in different calls are independent. The cost is that those variables cannot be garbage collected while the closure is alive."
</Callout>

## The loop and setTimeout puzzle

**In simple words:** the classic trick question. It is really a `var` versus `let` question wearing a costume.

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3 3 3

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0 1 2
```

**Why.** `var` is function scoped, so there is exactly **one** `i` for the whole loop. All three callbacks close over that same variable. By the time the timers fire, the loop has finished and `i` is 3.

`let` is block scoped, and the `for` loop creates a **fresh binding on every iteration**. Three separate variables, three separate closures, three different values.

### Three ways to fix the var version

```js
// 1. Use let. Always the right answer in real code.
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);

// 2. IIFE - create a new scope by hand, the pre-ES6 fix
for (var i = 0; i < 3; i++) {
  (function (captured) {
    setTimeout(() => console.log(captured), 0);
  })(i);
}

// 3. Pass the value through setTimeout's extra arguments
for (var i = 0; i < 3; i++) {
  setTimeout((captured) => console.log(captured), 0, i);
}
```

<Callout variant="careful">
The timers are not the point. Replace `setTimeout` with pushing functions into an array and calling them later — same result. The question is about *when the variable is read*, not about timing.
</Callout>

## this

**In simple words:** in a normal function, `this` is decided by **how the function is called**, not where it was written. Four rules, checked in order.

| # | Rule | How it looks | What `this` is |
| --- | --- | --- | --- |
| 1 | `new` binding | `new Person()` | the brand new object |
| 2 | Explicit binding | `fn.call(obj)`, `fn.apply(obj)`, `fn.bind(obj)` | whatever you passed |
| 3 | Implicit binding | `obj.method()` | the object left of the dot |
| 4 | Default binding | `fn()` | `undefined` in strict mode, `globalThis` otherwise |

Arrow functions sit outside this list entirely. **An arrow function has no `this` of its own.** It uses the `this` from wherever it was written, and nothing can change that — not `call`, not `bind`.

```js
const user = {
  name: "Subham",
  greet() {
    console.log(this.name);
  },
};

user.greet();                 // "Subham"  -- rule 3, object left of the dot

const detached = user.greet;
detached();                   // undefined -- rule 4, the dot is gone

setTimeout(user.greet, 0);    // undefined -- same problem, passed as a plain fn
setTimeout(() => user.greet(), 0);  // "Subham" -- the dot survives
```

<Callout variant="work" label="The bug you have actually hit">
This is why a React class method passed as `onClick={this.handleClick}` used to lose `this`. Passing a method as a value strips the object it came from. The fixes were `this.handleClick = this.handleClick.bind(this)` in the constructor, or defining it as a class property arrow function.
</Callout>

<Callout variant="interview">
"In a normal function `this` is determined at call time by four rules, in priority order: `new`, then explicit binding with call, apply or bind, then implicit binding from the object before the dot, then the default which is undefined in strict mode. Arrow functions do not follow those rules at all — they capture `this` lexically from where they were defined, which is why they are the right choice for callbacks inside a method."
</Callout>

## call, apply and bind

**In simple words:** three ways to say "run this function, but with `this` set to something I choose".

- `call(thisArg, a, b)` — runs immediately, arguments listed
- `apply(thisArg, [a, b])` — runs immediately, arguments in an array
- `bind(thisArg, a)` — does **not** run, returns a new function with `this` locked in

```js
function introduce(greeting, punctuation) {
  return `${greeting}, I am ${this.name}${punctuation}`;
}

const me = { name: "Subham" };

introduce.call(me, "Hello", "!");     // "Hello, I am Subham!"
introduce.apply(me, ["Hi", "."]);     // "Hi, I am Subham."

const boundIntro = introduce.bind(me, "Hey");
boundIntro("!!");                     // "Hey, I am Subham!!"
```

### Implement your own bind

A very common senior-round request. Three things must work: `this` binding, partial application, and behaving correctly when the bound function is called with `new`.

```js
Function.prototype.myBind = function (thisArg, ...boundArgs) {
  const originalFn = this;

  if (typeof originalFn !== "function") {
    throw new TypeError("Bind must be called on a function");
  }

  function bound(...callArgs) {
    // when used with `new`, ignore thisArg and use the fresh object
    const isNew = this instanceof bound;
    return originalFn.apply(isNew ? this : thisArg, [...boundArgs, ...callArgs]);
  }

  bound.prototype = Object.create(originalFn.prototype || null);
  return bound;
};
```

<Callout variant="careful">
`bind` returns a **new** function every time you call it. `element.removeEventListener("click", this.handler.bind(this))` never removes anything, because that is a different function object from the one you added. Bind once, store it, then add and remove that stored reference.
</Callout>

## Arrow functions vs regular functions

**In simple words:** arrows are not just shorter syntax. They are missing several things on purpose.

| | Regular function | Arrow function |
| --- | --- | --- |
| `this` | set at call time by the four rules | inherited from where it was written |
| `arguments` object | yes | no, use rest parameters |
| Usable with `new` | yes | no, throws TypeError |
| Has a `prototype` property | yes | no |
| Can be a generator | yes | no |
| Hoisting | declarations hoist fully | only the variable hoists |

**When you must not use an arrow:**

```js
// 1. As an object method that needs `this`
const counter = {
  count: 0,
  bad: () => { this.count++; },      // `this` is not counter
  good() { this.count++; },
};

// 2. As a constructor
const Person = (name) => { this.name = name; };
new Person("Subham");                 // TypeError: not a constructor

// 3. As a prototype method
Dog.prototype.speak = () => this.name; // `this` is not the instance
```

**When an arrow is exactly right:** any callback inside a method, where you want the surrounding `this`.

```js
class Timer {
  constructor() { this.seconds = 0; }
  start() {
    setInterval(() => { this.seconds++; }, 1000);  // arrow keeps `this`
  }
}
```

## Closures you actually write

**In simple words:** closures are not a puzzle-only feature. Almost every utility function you use is one.

### Private state

```js
function createAccount(initial) {
  let balance = initial;                  // genuinely unreachable from outside

  return {
    deposit(amount) { balance += amount; return balance; },
    getBalance() { return balance; },
  };
}

const account = createAccount(100);
account.deposit(50);   // 150
account.balance;       // undefined -- there is no way in
```

### once

```js
function once(fn) {
  let called = false;
  let result;

  return function (...args) {
    if (called) return result;
    called = true;
    result = fn.apply(this, args);
    return result;
  };
}

const init = once(() => console.log("setting up"));
init();  // logs
init();  // silent
```

### memoize

```js
function memoize(fn, keyFrom = (...args) => JSON.stringify(args)) {
  const cache = new Map();

  return function (...args) {
    const key = keyFrom(...args);
    if (cache.has(key)) return cache.get(key);

    const value = fn.apply(this, args);
    cache.set(key, value);
    return value;
  };
}
```

<Callout variant="careful">
That `cache` never shrinks. In a long-running Node process a memoized function called with many different arguments is a slow memory leak. Real implementations add a size cap or a TTL. Say this out loud in an interview — it is the detail that separates a memorised answer from an understood one.
</Callout>

## Currying and partial application

**In simple words:** currying turns a function that takes three arguments into a chain of functions that each take one. Partial application just pre-fills some arguments and waits for the rest.

```js
// plain
const add = (a, b, c) => a + b + c;
add(1, 2, 3);          // 6

// curried
const curriedAdd = (a) => (b) => (c) => a + b + c;
curriedAdd(1)(2)(3);   // 6
```

### A generic curry

```js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {
      return fn.apply(this, args);
    }
    return (...rest) => curried.apply(this, [...args, ...rest]);
  };
}

const sum = curry((a, b, c) => a + b + c);
sum(1)(2)(3);      // 6
sum(1, 2)(3);      // 6
sum(1)(2, 3);      // 6
```

`fn.length` is the number of declared parameters. The moment enough have arrived, it runs.

### Infinite currying

A separate puzzle. `sum(1)(2)(3)()` — the empty call signals the end.

```js
function sum(a) {
  let total = a;
  function next(b) {
    if (b === undefined) return total;
    total += b;
    return next;
  }
  return next;
}

sum(1)(2)(3)();   // 6
```

## IIFE and the module pattern

**In simple words:** an IIFE is a function you define and call in the same breath. Before ES modules existed, it was the only way to get a private scope.

```js
(function () {
  // everything here is invisible to the outside
})();

const CounterModule = (function () {
  let count = 0;                              // private
  return {
    increment() { return ++count; },
    reset() { count = 0; },
  };
})();
```

You rarely write these now — every ES module already has its own scope. But you will see them constantly in older code and in bundled output, so recognise the shape.

## Composition and pipe

**In simple words:** small functions combined into bigger ones. `pipe` reads left to right, `compose` reads right to left.

```js
const pipe = (...fns) => (input) => fns.reduce((acc, fn) => fn(acc), input);
const compose = (...fns) => (input) => fns.reduceRight((acc, fn) => fn(acc), input);

const trim = (s) => s.trim();
const lower = (s) => s.toLowerCase();
const slugify = (s) => s.replace(/\s+/g, "-");

const toSlug = pipe(trim, lower, slugify);
toSlug("  Hello World  ");   // "hello-world"
```

<Callout variant="work" label="Where you have already used this">
Redux middleware is `compose`. Express middleware is a `pipe` with an escape hatch. Once you see the shape you start noticing it everywhere.
</Callout>

Answer each out loud before revealing.

<Quiz>
  <QuizItem number={1} question={<>Explain a closure to someone who has never heard the word, in two sentences.</>}>
    <p>A function that remembers the variables that were around it when it was created, even after the code that created them has finished running. Each time you run the outer function you get a fresh, independent set of those variables.</p>
    <p>If you started with the word &quot;scope&quot; or &quot;execution context&quot;, try again — the interviewer is testing whether you can explain it, not recite it.</p>
  </QuizItem>

  <QuizItem number={2} question={<>Why does a <code>var</code> loop with <code>setTimeout</code> print 3 3 3, and what are three ways to fix it?</>}>
    <p><code>var</code> is function scoped, so there is one shared <code>i</code>. All three callbacks close over that same variable, and by the time the timers run the loop has ended with <code>i</code> at 3.</p>
    <p>Fixes: use <code>let</code>, which creates a fresh binding each iteration; wrap the body in an IIFE that takes <code>i</code> as a parameter; or pass <code>i</code> as a third argument to <code>setTimeout</code>.</p>
  </QuizItem>

  <QuizItem number={3} question={<>What is <code>this</code> inside a method that has been passed as a callback, and how do you fix it?</>}>
    <p><code>undefined</code> in strict mode, or the global object otherwise. Passing <code>obj.method</code> as a value strips the object before the dot, so the implicit binding is gone and the default rule applies.</p>
    <p>Fix by wrapping in an arrow — <code>() =&gt; obj.method()</code> — or by binding once and storing the result.</p>
  </QuizItem>

  <QuizItem number={4} question={<>Name the four rules for <code>this</code> in priority order, and say where arrow functions fit.</>}>
    <p>1. <code>new</code> binding. 2. Explicit binding with call, apply or bind. 3. Implicit binding from the object before the dot. 4. Default binding, undefined in strict mode.</p>
    <p>Arrow functions do not participate. They have no <code>this</code> of their own and take it lexically from the enclosing scope, which is why <code>call</code> and <code>bind</code> cannot change it.</p>
  </QuizItem>

  <QuizItem number={5} question={<>Name four concrete differences between an arrow function and a regular function.</>}>
    <p>Arrows take <code>this</code> lexically instead of at call time. They have no <code>arguments</code> object. They cannot be used with <code>new</code>. They have no <code>prototype</code> property, and they cannot be generators.</p>
    <p>Follow-up you should expect: when must you NOT use one? As an object method or prototype method that needs <code>this</code>, and as a constructor.</p>
  </QuizItem>

  <QuizItem number={6} question={<>Why does this fail to remove the listener? <code>el.removeEventListener(&quot;click&quot;, this.handler.bind(this))</code></>}>
    <p><code>bind</code> returns a brand new function every time it is called. The function passed to <code>removeEventListener</code> is a different object from the one that was added, so nothing matches and nothing is removed.</p>
    <p>Bind once, store the result on the instance, then use that same reference for both add and remove.</p>
  </QuizItem>

  <QuizItem number={7} question={<>What is the memory cost of a closure, and when does it become a real leak?</>}>
    <p>A closure keeps its captured variables alive for as long as the closure itself is reachable, so they cannot be garbage collected.</p>
    <p>It becomes a leak when the closure outlives its usefulness — an event listener that is never removed, an interval that is never cleared, or an unbounded memoisation cache in a long-running Node process.</p>
  </QuizItem>

  <QuizItem number={8} question={<>How does a generic <code>curry</code> know when to stop collecting arguments and actually run?</>}>
    <p>It compares the number of collected arguments against <code>fn.length</code>, which is the count of declared parameters. Once enough have arrived it applies the original function; otherwise it returns another collector.</p>
    <p>Worth noting the limitation: <code>fn.length</code> ignores rest parameters and parameters with defaults, so currying does not work on those.</p>
  </QuizItem>

  <QuizItem number={9} question={<>How would you give an object genuinely private state, without <code>#</code> fields?</>}>
    <p>Declare the variable inside a factory function and return only the methods that need it. The variable is in the closure scope, so there is no property to read, no key to enumerate, and no way in from outside.</p>
    <p>This is the module pattern, and it was the standard approach before private class fields existed.</p>
  </QuizItem>

  <QuizItem number={10} question={<>What does <code>once(fn)</code> need to remember, and why must it store the result rather than just a flag?</>}>
    <p>It needs a boolean for whether it has run, and the return value from that first run.</p>
    <p>Storing only the flag would make every call after the first return <code>undefined</code>, which is almost never what the caller wants. The point is that repeat calls behave as if they had run and got the same answer.</p>
  </QuizItem>
</Quiz>
